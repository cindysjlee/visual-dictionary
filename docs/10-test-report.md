기준 시점: 2026-11-26. 공개 용어는 20개(published, 6개를 11-25에 공개. 우선순위 역전은 draft)이고, CI 45615789172(커밋 `19cd0bd`)에서 배포됐다(그 앞 배포는 11-24 CI 45255574801, 그때 공개 용어는 14개). 설명 틀·각주, 용어 쪽 머리 영역, 화면 이동 스크롤·`useJson` 수정, 완독 자동 기록, 5개 shard CI도 그 배포에 들어 있다. 2절·성능 기준 표의 smoke·check:aws·LCP 수치는 11-24 배포(용어 14개) 때 잰 값이고, 11-26 배포 뒤에는 CI 안의 smoke:prod·check:aws만 돌았다(4절). 이전 기준(11-21 콘텐츠 1차·중간 점검 4차)의 수치는 바뀐 항목만 고쳤다. 아래 단위·E2E 개수는 11-26 기준이고, E2E 전체 통과 수는 2절 표에 적었다(빌드 513 통과, 초안 포함 524 통과·1 건너뜀). 요구사항별 테스트 연결은 `09-traceability.md`, 테스트가 잡은 결함의 자세한 내용은 `08-defect-log.md`에 있다.

- 측정 조건: 네트워크를 Lighthouse 데스크톱 조건(왕복 40ms, 10Mbps)으로 늦추고, 로컬 테스트 빌드(`dist-e2e`)를 대상으로 E2E 병렬 실행(workers 4) 중에 잰다. CDN까지의 거리와 운영 캐시는 들어가지 않는다.
- 테스트 빌드에는 장면 기록 코드가 있어 운영 묶음보다 조금 크다. 그래서 운영보다 불리한 쪽으로 잰다.
- **어디서 실패로 보나**: LCP·CLS 기준 초과는 **로컬 배포 전 전체 E2E에서만 실패**다. CI(GitHub 러너)에서는 `@perf`가 측정값과 기준 이내 여부만 작업 요약(Job summary)에 남기고 실패로 보지 않는다(측정이 안 되는 경우, 즉 LCP 0만 실패). 이유: 러너는 GPU가 없고 공유 장비라 실행마다 성능 편차가 커서, 기준 초과가 화면 회귀가 아니라 러너 상태 때문일 수 있다. 같은 이유로 실제 속도 E2E 2개도 CI에서 돌리지 않는다. draft 검사(`test:e2e:drafts`)도 번들하지 않는 개발 서버를 재므로(LCP 6~7초) 측정만 하고 실패로 보지 않는다.
- 기록 API 응답 시간은 이 컴퓨터(서울 근처)에서 운영 CloudFront를 거쳐 잰 왕복 시간이다. 같은 사용자의 앞선 호출로 Lambda가 데워진 뒤에 재므로 첫 호출(콜드 스타트)은 포함하지 않는다.

### 3D 저사양 경로와 프레임 속도(11-24)

**저사양에서 바뀌는 것(코드 확인, `players/three/SceneCanvas.tsx`).** 툰 재질·외곽선(셀 셰이딩)을 되돌리면서(docs/06 "종이 장면") 그때 넣었던 저화질 모드도 함께 빠졌다. 지금 기기 성능에 따라 바뀌는 것은 다음뿐이다.
- 좁은 화면(`mobile`): 그림자 맵 1024(넓은 화면 1536). 해상도 배율 `dpr [1, 2]`, 그림자 켜짐, 안티에일리어싱은 모든 화면에서 같다.
- 무대가 화면 밖이거나 탭이 숨으면 그리기를 멈춘다(`frameloop`).
- 동작 줄이기면 움직임 없이 단계 결과만 보인다. WebGL을 쓸 수 없으면 2D 단계 목록으로 대신한다.

**측정.** 운영 빌드 미리보기(`vite preview`)를 Playwright(설치된 Chrome)로 열고, 재생을 시작한 뒤 8초 동안 `requestAnimationFrame` 간격을 쟀다. CPU 느리게는 Chrome DevTools `Emulation.setCPUThrottlingRate`(4배). 이 컴퓨터의 GPU는 Intel Iris Xe(내장)이고, CPU 느리게는 GPU를 느리게 하지 않는다.

## 5. 확인하지 못한 것

- **스크롤 위치 복원 테스트는 개발 서버(초안 포함 실행)에서 건너뛴다**: "뒤로 가기: #term-fig로 연 용어 쪽에서 …" 한 개는 개발 서버에서는 CSS·글꼴이 늦게 들어와 높이가 바뀌어 복원 위치가 어긋난다(공개된 xss도 같은 증상이라 용어 내용 문제가 아니다). 빌드를 쓰는 실행(`npm run test:e2e`)에서만 돌고, 원인은 더 조사하지 않았다.
- **설명 틀 전환**: 우선순위 역전을 뺀 모든 용어가 설명 틀이다(우선순위 역전은 "(설명 준비 중)" 초안). 개념과 문장의 정확성은 사용자가 묶음마다 검수했고, 근거로 연 문서는 묶음 보고에 적었다. TCB(스레드 제어 블록)는 연 문서(Wikipedia Context switch)에 직접 나오지 않아 시나리오 설명을 따랐다.
- **draft 7개의 사람 검수**: 장면·자막은 스크린샷으로 단계마다 대조했지만 개념 검수(status를 published로 바꾸기 전)는 사용자가 한다. 페이지 폴트는 RAM 이름표가 커널 모형 위에 놓이는 단계가 있다(docs/04 "새 어휘가 필요해…").
- **글자 대비는 이번 CSS 변경에서 색을 바꾸지 않았다**: 머리 영역 배치와 줄 길이만 바꿨고, 새 색은 없다. axe(라이트·다크)와 각주 대비 E2E로 확인했다.
- **smoke:auth:signup**: 8단계(구글 로그인, 인증 코드 변경) 뒤에는 다시 돌리지 않았다. CLAUDE.md는 인증 코드를 바꿔 배포했을 때 돌리게 되어 있다.
- **성능 측정 범위**: LCP·CLS는 운영 CDN이 아니라 로컬 테스트 빌드 기준이고, 기록 API 응답 시간은 Lambda 콜드 스타트를 뺀 값이다.
- **CI의 새 E2E**: 2차의 37개는 CI 44795013341, 3차의 `@wide` 14개는 CI 44801749175에서 통과했다. 4차부터 CI의 `@perf`는 측정만 하고 판정하지 않는다(2절).
- **실제 메일·구글 경로**: 가입·재설정 메일과 구글 로그인은 사람이 직접 확인했고 자동 테스트는 가짜 구현 위에서만 돈다.
- **고아 정리 일정의 정기 실행(일부만 확인, 11-24 조회)**: 03:00(KST)에 시작한 실행이 11-22·11-23·11-24에 하나씩 함수 로그에 남아 있고 모두 `status: done`이다(찾은 고아는 각각 4명·0명·1명, `ERROR`가 든 로그 없음). 그 고아가 누구였는지와 정리 결과(기록이 실제로 지워졌는지)는 조회하지 않았다. 실행을 일으킨 쪽(Scheduler)은 로그로 확인하지 않았고 일정 시각과 같다는 것만 봤다. smoke는 함수를 직접 실행해 확인한다.
- **실제 속도 E2E 2개**: GPU가 없는 CI에서는 돌지 않고 로컬 전체 E2E에서만 돈다.
- **3D 프레임 속도**: 이 컴퓨터(Intel Iris Xe)에서 CPU만 4배 느리게 해서 쟀다. 실제 휴대폰 GPU·열 제한은 재지 않았다.
- **운영 화면의 完 도장·책갈피**: 운영에서는 smoke:progress가 진행률 문구만 확인한다. 도장 모양과 책갈피 규칙은 개발 서버 화면과 E2E(가짜 API)로 확인했다.
