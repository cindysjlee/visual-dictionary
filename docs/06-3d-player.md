# 3D 플레이어 설계

애니메이션 플레이어를 2D(SVG + Framer Motion)에서 **실시간 3D(three.js + React Three Fiber)** 로 바꾼다.
기준 시안: `docs/design/csrf-3d-prototype.html` (CSRF 한 편, 공격 흐름·방어 모드·자유 시점 포함).
시안은 CDN에서 three.js r128을 불러오는 단일 HTML이다. 브라우저로 열어 재생해 볼 수 있다. 코드는 동작 참고용이고, 그대로 옮기지 않는다.

## 1. 왜 3D인가 (지켜야 할 핵심)

3D를 "옆에서 본 일자 배치"로 쓰면 2D와 차이가 없다. 아래 세 가지가 3D를 쓰는 이유이고, 모든 용어 장면에서 유지한다.

1. **공간이 곧 개념이다.** 배치 자체가 설명이 되게 한다. 예: 사용자 쪽(브라우저)은 앞, 서버는 인터넷 너머 뒤쪽 섬. 같은 브라우저 상자 안에 두 탭과 쿠키 보관함이 있어서, 어느 탭이 보냈든 같은 쿠키가 붙는다는 게 보인다.
2. **카메라가 설명한다.** 단계마다 카메라가 그 단계에 나오는 것 전체(출발지·목적지·경유지·효과 대상)를 한 화면에 담고, 쿠키를 붙이거나 검문하거나 탭을 뒤집는 세부 순간에만 잠깐 다가간다(3절 "카메라 규칙"). 사용자가 시점을 돌리는 건 "자유 시점"을 켰을 때만 된다.
3. **물체의 앞뒤·안쪽을 쓴다.** 탭을 뒤집어 숨은 폼을 보여주고, 검문소에서 봉투를 열어 내용물(쿠키, 토큰)을 꺼내 검사한다.

## 2. CSRF 장면 (시안 기준)

### 배치 (월드 좌표, 단위는 three.js 기본)

| 대상 | 위치 | 설명 |
| --- | --- | --- |
| 브라우저 | (0, 0, 2.2) | 유리 상자 6.0×3.0×2.8, 상단바, 바닥판 |
| 은행 탭 / 함정 탭 | 브라우저 안 x = -1.45 / +1.45 | 앞면·뒷면이 있는 패널. 함정 탭은 3단계에 생긴다 |
| 쿠키 보관함 | 브라우저 안 앞쪽 가운데 | 유리병. 쿠키가 들어가고 나온다 |
| 은행 서버 섬 | (-5, 0, -4.2) | 건물, 금고 문, 섬 앞쪽에 검문소(기둥 2개, 스캔 링, 차단봉) |
| 함정 사이트 서버 섬 | (5, 0, -4.2) | 어두운 탑, 공격색 줄무늬 |
| 공격자 섬 | (8.6, 0, 1.6) | 후드 인물 |
| 인터넷 | 바닥 점선 | 탭 ↔ 서버 연결선 |

### 단계별 연출과 카메라

| 단계 | 연출 | 카메라 |
| --- | --- | --- |
| 1 정상 로그인 | 은행 탭 → 검문소(차단봉 올라감) → 은행 | 은행 쪽 샷, 봉투 따라가기 |
| 2 세션 쿠키 발급 | 쿠키를 단 봉투가 은행 → 은행 탭, 쿠키가 보관함으로 떨어짐. **방어 모드:** 열쇠(CSRF 토큰)가 은행 탭 안으로 들어감 | 전체 → 보관함 근접 |
| 3 함정 링크 전송 | 공격자 → 브라우저, 함정 탭이 커지며 등장 | 공격자 쪽 → 브라우저 |
| 4 함정 사이트 접속 | 함정 탭 ↔ 함정 서버 왕복, 이벤트 화면 표시 후 **탭이 뒤집혀 뒷면의 숨은 폼이 드러남** | 함정 서버 → 함정 탭 근접 |
| 5 위조된 송금 요청 | 숨은 폼에서 봉투 출발 → 보관함 앞에서 "목적지 bank.example → 쿠키 자동 첨부" 표시, 쿠키가 봉투에 붙음 → 검문소에서 봉투가 열리고 내용 카드가 나옴. 공격: "쿠키 있음 / 토큰 검사 안 함" → 통과. **방어: "토큰 비어 있음" → 검문소가 방어색으로 바뀌고 403 도장, 봉투가 튕겨 떨어짐(재생 종료)** | 보관함 → 검문소 근접 → 은행 |
| 6 송금 완료 | 금고 문이 열리고 동전이 큰 포물선으로 공격자 섬에 날아감, 잔액이 줄어듦 | 전체(오른쪽으로 치우친) 샷 |

### 꼭 옮길 동작

- **가림 자동 투명:** 매 프레임 카메라 → (카메라 초점, 날아가는 봉투, 이 단계의 등장 행위자 각각)으로 선을 쏴서, 그 선을 막는 물체만 불투명도 10%까지 서서히 낮춘다. **모든 행위자**(건물·섬·탭·상단바 등)가 대상이지만, 이 단계의 등장 행위자 자신은 흐리지 않는다(보여 줘야 할 것이므로). 등장 행위자끼리 가리는 것은 배치·카메라와 겹침 검사가 막는다. 가리지 않으면 원래대로 돌아온다. 자유 시점에서도 동작한다.
- **라벨은 HTML:** 행위자 이름, 요청 라벨, 잔액, 검사 목록은 3D 텍스트가 아니라 화면 위 HTML로 띄운다(drei의 `Html` 또는 직접 투영). 글자가 선명하고 테마 토큰을 그대로 쓸 수 있다.
- **봉투·쿠키·열쇠는 항상 카메라를 향한다**(빌보드). 어느 각도에서도 모양이 읽혀야 한다.
- **색은 docs/05 토큰을 쓴다.** 런타임에 CSS 변수(`--attack`, `--defense`, `--neutral`, 면 색 등)를 읽어 재질에 넣고, 테마가 바뀌면 다시 읽는다. 장면 코드에 색 값을 직접 쓰지 않는다.
- **공격·방어 구분:** 공격 단계는 공격색, 차단 순간은 방어색(봉투 날개, 스캔 링, 차단봉, 도장). 색만이 아니라 형태로도 구분한다(도장, 방패·열쇠 모양).

### 생김새 (`look`)

같은 `kind`(특히 서버)가 모두 똑같이 생기면 구분이 안 되므로, 행위자에 `look`을 적어 생김새를 고른다(`docs/04`). 모두 기본 도형 조합이고 외부 모델 파일은 쓰지 않는다(`players/three/model.ts`의 `buildLook`). `look`이 없으면 `kind`의 기본 모양 그대로다.

| look | kind | 모양 | 쓰는 곳 |
| --- | --- | --- | --- |
| `bank` | server | 기둥 건물(지붕·기둥 4개) + 오른쪽 앞 금고(상자 + 둥근 문 + 손잡이), 지붕 앞 간판 | CSRF 은행 |
| `web` | server | 랙 서버(납작한 칸 4개 + 표시등·슬롯) + 위 모니터 간판 | SQL 인젝션·SSRF 웹 서버 |
| `shop` | server | 상점 몸통(문·창) + 줄무늬 차양 + 지붕 위 간판 | 세션 하이재킹 쇼핑몰 |
| `community` | server | 상점 몸통 + 앞 게시판(기둥 2개 위 판, 간판 역할) + 지붕 위 말풍선 | XSS 커뮤니티 |
| `database` | server·database | 층층 원통 3단 + 뚜껑 | SQL 인젝션 회원 DB |
| `cloud-metadata` | server | 구름 받침(구 4개) + 칩 상자(핀·코어) + 그 위 주소판 | SSRF 메타데이터 서비스 |
| `wifi` | network | 공유기 상자 + 안테나 2개 + 전파 고리 3개(반원) | 세션 하이재킹 공용 와이파이 |

- **간판·주소판에는 `site`를 글자로** 그린다(캔버스 텍스처, 테마가 바뀌면 다시 그림). HTML 이름 라벨이 가려져도 건물만 보고 구분된다.
- **wifi 전파 고리는 그 길목을 지나는 봉투가 가까이(3.2) 있을 때만** 바깥으로 퍼진다(단계의 출발·경유·목적지에 그 와이파이가 있을 때). 동작 줄이기에서는 멈춰 있다. 테스트 빌드는 고리 시작·멈춤을 `ringsStart`·`ringsEnd`로 기록하고 E2E가 확인한다.
- **공격 쪽(`tone: "attack"`)** 은 어떤 look이든 어두운 재질에 공격색 띠를 두른다(색만이 아니라 형태로도 구분). look이 없는 공격 서버는 기존의 어두운 줄무늬 탑이다.

## 3. 데이터 주도 원칙 (용어 = JSON 하나)

3D가 되어도 **용어별로 장면 코드를 따로 쓰지 않는다.** 플레이어가 JSON을 읽어 장면을 만든다.

- 행위자는 **종류(kind)** 로 모양이 정해지고, **구역(zone)** 으로 위치가 자동 배치된다. 좌표를 JSON에 직접 쓰지 않는다.
- 단계의 연출은 정해진 **효과 어휘(effects)** 로만 적는다.
- **카메라 규칙** (`players/three/director.ts`의 `CameraRig.frame`, `buildStep`)
  - **기본은 등장 행위자 전체 샷:** 단계가 시작되면 등장 행위자(출발·목적지·경유지·효과 대상)와 그 이름표가 모두 화면 안쪽 82%에 들어오는 가장 가까운 거리(최소 9)로 맞춘다. 화면 비율을 반영하고, 원근 때문에 어긋나는 가운데를 투영 범위 기준으로 보정한다. 위에서 약 40° 내려다본다.
  - **세부 순간만 근접:** 쿠키 붙이기·검문(봉투 열기)·탭 뒤집기·보관함 넣기·화면 고쳐 쓰기·스크립트 실행·차단 도장은 잠깐 다가갔다가, 단계 끝에는 다시 등장 행위자 전체 샷으로 물러나 대기한다.
  - **목적지는 처음부터 화면에:** 봉투가 멀리 날아가는 단계에서도 출발 샷이 목적지를 담는다. 아직 숨은 대상(이 단계에 `appear`로 나타날 탭 등)은 나타날 자리(배치 위치와 이름표 자리)로 담는다. 단계 끝에는 목적지와 효과 대상이 화면 안에 있어야 한다. 용어별 예외 없이 모든 단계에 같은 규칙이다(예전에는 CSRF 3단계에서 함정 탭이 숨은 채라 카메라가 공격자만 비췄다).
  - **바꾼 이유(가독성):** 처음 방식(봉투를 따라가며 효과 대상마다 근접)은 화면이 계속 움직여, 지금 무엇이 어디로 가는지와 무엇이 무엇을 가리는지 알기 어려웠다. 등장 행위자를 한 화면에 두면 자막과 장면을 같이 읽을 수 있고, 겹침·가림을 검사(7절)로 막을 수 있다.
  - 필요할 때만 `camera` 힌트로 덮어쓴다(힌트 대상도 마지막 샷에 함께 담는다).
- 배치 간격(`players/three/layout.ts`): 구역 줄 사이를 넓게 띄우고, 같은 줄에 둘 이상이면 하나 걸러 받침으로 높이고(0.9) 뒤로 물린다(1.4). 브라우저 이름표는 상자 왼쪽 바깥, 서버·인물이 가진 물건은 오른쪽 앞에 둔다. 행위자 이름·잔액 라벨은 재생 중에도 서로 겹치면 위로 비킨다.

아래는 제안이다. 최종 스키마는 기존 `docs/04` 형식과 호환되게 정하고, 사용자 승인 후 확정한다.

```jsonc
"scene": {
  "actors": [
    { "id": "browser",  "kind": "browser",   "zone": "client" },
    { "id": "bankTab",  "kind": "tab",       "parent": "browser", "site": "bank.example" },
    { "id": "evilTab",  "kind": "tab",       "parent": "browser", "site": "evil.example", "tone": "attack", "appearAt": 3 },
    { "id": "jar",      "kind": "cookieJar", "parent": "browser" },
    { "id": "bank",     "kind": "server",    "zone": "server", "site": "bank.example", "gate": true },
    { "id": "evil",     "kind": "server",    "zone": "server", "site": "evil.example", "tone": "attack" },
    { "id": "attacker", "kind": "attacker",  "zone": "outside" }
  ]
},
"steps": [
  { "title": "세션 쿠키 발급", "from": "bank", "to": "bankTab", "label": "Set-Cookie: session",
    "effects": [ { "type": "storeCookie", "into": "jar" },
                 { "type": "giveToken", "to": "bankTab", "mode": "defense" } ] },
  { "title": "함정 사이트 접속", "from": "evilTab", "to": "evil", "label": "GET /event", "roundTrip": true,
    "effects": [ { "type": "flip", "target": "evilTab", "reveal": "숨은 폼" } ] },
  { "title": "위조된 송금 요청", "from": "evilTab", "to": "bank", "label": "POST /transfer",
    "effects": [ { "type": "attachCookie", "from": "jar" },
                 { "type": "inspect", "at": "bank", "checks": ["cookie", "csrfToken"] } ] }
]
```

확정된 어휘는 `docs/04`의 "3D 장면 필드"가 기준이다(구역 `between`, 경유 `via`, 제자리 단계, 서버·DB 화면판, `attach.note`, 검사 없는 차단의 도장 위치 포함). 아래는 처음 제안할 때의 초안이다.

효과 어휘 초안: `appear`, `flip`, `storeCookie`, `attachCookie`, `giveToken`, `inspect`, `transfer`(동전·데이터가 넘어감), `stamp`(차단 도장, 방어 모드 차단 단계에 자동). 방어 모드의 차단은 지금처럼 `defenses[].blockedAtStep`이 결정하고, 차단 단계에서는 `inspect` 결과가 실패로 바뀐다.

**방어 모드와 해결 방법:** 보안 용어의 방어(`kind: defense`)는 `blockedAtStep`에서 차단 연출을 하고 멈춘다. CS 용어의 해결 방법(`kind: solution`)은 `branchAtStep`부터 대체 흐름(`steps`)을 끝까지 재생한다(멈추지 않음). 3D 장면은 `stepView`가 모드에 맞는 단계를 돌려주므로 두 방식을 따로 그리지 않는다. 형식은 `docs/04` "방어 모드 동작"·"해결 방법 동작".

**다른 플레이어 유형** (4단계에서 확정, 어휘는 `docs/04` 스택형·점유형 절)
- **스택형(콜 스택)** (`players/three/stack/`, 4b에서 확정)
  - **공간이 개념:** 왼쪽에 코드 판(C·Java에 가까운 의사코드, 실행 중인 줄 ▶ 강조), 오른쪽에 유리 기둥. 프레임이 위로 쌓이고 높이가 곧 호출 깊이다. 실행 중인 맨 위 프레임만 테두리가 진하고, 아래 프레임은 흐리게 기다린다. 실제 메모리에서는 스택이 보통 낮은 주소 쪽으로 자라지만 여기서는 위로 쌓아 표현한다(용어 설명에 적음).
  - **물체의 안쪽:** 프레임 앞면 판에 호출식과 지역 변수 칸(`n = 2`, `계산 = 2 × ▢`)이 있고, 옆 꼬리표에 반환 주소(`↩ factorial 3행`)가 있어 코드 판의 그 줄(↩ 표시)까지 금색 실로 이어진다. 같은 함수의 프레임이 여러 개여도 칸이 따로라 재귀가 보인다.
  - **연출:** push는 새 프레임이 위에서 내려와 앉는다. pop은 반환값 구슬(`return 1` 라벨)이 실처럼 아래 프레임 판으로 날아가 빈칸을 채우고, 맨 위 프레임이 위로 빠지며 사라진 뒤 아래 프레임 판이 새 값으로 바뀐다. run은 맨 위 프레임이 살짝 뛰고 코드 판의 줄이 옮겨 간다.
  - **카메라:** 거의 정면(약 20° 위)에서 코드 판 전체와 쌓인 프레임, 다음 자리까지 담는다. 쌓일수록 위로 올라간다.
  - **검사:** 장면 기록은 `push`·`pop`·`run`과 `effect`(returnValue → locals 순)를 남긴다. 겹침 검사는 코드 판·맨 위 프레임·바로 아래 프레임.
- **점유형(데드락)** (`players/three/lock/`, 4c에서 확정)
  - **공간이 개념:** 앞줄에 스레드(인형), 뒷줄 받침대에 자원(프린터·스캐너 look). 쥐면 자원이 받침대에서 스레드 몸 옆으로 오고 받침대 자물쇠가 잠긴다. 기다리면 스레드 위에 모래시계, 기다리는 자원까지 공격색 점선.
  - **네 조건:** 상호 배제 = 잠긴 자물쇠(한 번에 한 스레드), 점유 대기 = 한 손에 자원을 든 채 점선으로 기다림, 순환 대기 = 바닥에 두 스레드를 두르는 고리가 생기고 카메라가 위로 올라가 고리 모양을 보여 줌, 비선점 = 상대 자원에 손을 뻗었다가 튕겨 나오며 "빼앗을 수 없음". 무대 왼쪽 위에 고정된 "교착 조건" 패널이 단계마다 한 칸씩 "성립"(공격색)으로 켜지고, 해결 방법이 깬 조건은 "깨짐"(방어색 굵게).
  - **해결 방법(대체 흐름):** 획득 순서 고정은 2단계에서 갈라져 B가 빈손으로 기다리고(순환 대기 깨짐) A 반납 → B 진행 → 둘 다 완료. 타임아웃은 5단계에서 갈라져 B가 기다리다 포기하고 쥔 스캐너를 스스로 내려놓아(점유 대기 깨짐) 고리가 풀린다. 끝 도장은 교착이면 공격색, 해결이면 방어색.
  - **카메라:** 기본은 그 단계의 스레드·자원(받침대 포함) 전체 샷, 순환 대기·도장 단계는 모두를 위에서(`TOP_VIEW`) 내려다본다.
  - **검사:** 장면 기록은 `acquire`·`wait`·`release`와 `effect`(조건 이름·빼앗기 대상·그 스레드). 겹침 검사는 스레드 인형·자원 본체 크기 기준(받침대·섬 제외).

## 4. 기술 구성

- `three`, `@react-three/fiber`(React 19에 맞는 버전), 필요하면 `@react-three/drei`(Html 라벨 등). 버전과 API는 context7로 확인한다.
- **PlaybackEngine은 그대로 순수 로직**이다(단계·재생·시작 여부·방어 모드·끝까지 봄 이벤트). 3D 장면은 엔진 상태를 읽어 그리기만 한다.
- 단계 안의 세부 움직임(포물선, 카메라 이동, 뒤집기)은 `useFrame` 기반의 작은 타임라인으로 만든다(시안의 tween 방식). 단계를 넘길 때는 진행 중인 타임라인을 취소하고, 이전 단계까지의 결과 상태를 즉시 적용한 뒤 현재 단계만 재생한다.
- 버튼·탭·자막 같은 일반 UI의 움직임은 계속 Framer Motion을 써도 된다.

## 5. 성능

- 3D 플레이어는 **상세 페이지에서만 동적 import**한다. 홈 번들에 three.js가 들어가면 안 된다.
- `dpr`은 최대 2. 그림자 맵은 1024~1536.
- 화면 밖에 있거나 탭이 숨겨지면 그리기를 멈춘다. 재생이 끝나 움직임이 없으면 필요할 때만 그린다(`frameloop="demand"` 등).
- 노트북 기준 60fps에 가깝게, 휴대폰(375px)에서도 버벅이지 않게 한다.

## 6. 접근성·대체 화면

- **자막만 읽어도 개념이 이해되어야 한다**(NFR-03). 3D는 보조 수단이다.
- 재생 컨트롤, 모드 탭, 자유 시점 버튼은 모두 실제 `button`이다. 자막은 `aria-live="polite"`. 캔버스는 `aria-hidden`이고, 대신 현재 단계 설명이 텍스트로 있다.
- **재생 시작:** 상세 진입 시 1단계 장면 전체를 보여 주고 멈춘다. 무대 가운데의 큰 재생 버튼(실제 `button`, `aria-label="재생"`), 아래 재생 버튼, 스페이스 중 무엇으로 시작해도 1단계 연출부터 끝까지 이어서 재생하고, 가운데 버튼은 사라진다. 단계 사이 대기는 `holdMs()`(`players/stage.ts`, 1× 기준): 3D는 0.8초 + 자막(제목+본문, 공백 제외) 글자당 35ms(최소 2초), 연출이 없는 화면(동작 줄이기·2D)은 1.5초 + 글자당 90ms(최소 2.6초).
- **재생 속도:** 0.75× / 1× / 1.5× / 2×(컨트롤 줄의 `select`, `aria-label="재생 속도"`). 장면 타임라인(연출 + 대기)을 같은 배수로 돌린다. 동작 줄이기에서는 연출이 없으므로 대기에만 걸린다. 고른 값은 `localStorage`(`playback-speed`)에 기억하고, 저장소를 못 쓰면 1×로 시작한다.
- **시작 전 전체 샷의 라벨:** 맨 위 행위자 이름만 보이고, 안에 든 것(탭·보관함)과 잔액은 재생하면 나타난다. 그래도 겹치면 뒤에 오는 라벨(JSON 행위자 순서)이 위로 비키고, 가운데 재생 버튼 자리도 비워 둔다. 데스크톱·375px 모두 라벨끼리, 라벨과 재생 버튼이 겹치지 않아야 한다.
- **동작 줄이기(`prefers-reduced-motion`):** 똑같이 멈춘 상태로 시작한다. 카메라 이동, 날아가기, 뒤집기 없이 각 단계의 결과 상태로 바로 바뀐다.
- **WebGL을 쓸 수 없을 때:** 단계 목록과 자막만 있는 2D 화면으로 대체한다. 이때도 방어 모드와 차단 단계 표시는 동작해야 한다.
- 자유 시점은 키보드로도 조작할 수 있게 하거나(화살표로 회전), 최소한 끄고 켤 수 있어야 한다.
- CSP는 그대로 둔다. three.js와 R3F는 번들에 포함되므로 `script-src 'self'`로 충분하다. 외부 CDN, `eval`, 인라인 스크립트를 쓰지 않는다.

## 7. 검증 (장면 기록)

- 테스트·개발 빌드(`import.meta.env.MODE !== "production"`)에서만 장면 타임라인이 `window.__sceneTrace`에 기록을 남긴다(`players/three/trace.ts`): 단계 시작, 봉투 출발(`depart`)·경유지(`via`)·검문소(`gate`)·도착(`arrive`)·왕복 귀환(`return`), 효과 실행(`effect`, 거부면 `refused`), 차단 도장(`blocked`), 단계 끝(`stepEnd`).
- 배포 빌드에서는 상수 조건으로 코드가 빠진다. `npm run check:bundle`이 배포 묶음에 `__sceneTrace`가 없는지 확인한다.
- 장면 기록 E2E는 순서 비교 외에 세 가지를 더 본다: 출발 샷이 목적지를 담는지(`depart.inShot`), 단계 끝에 카메라가 멈췄을 때 목적지·효과 대상이 화면 안에 있는지, wifi 전파 고리가 그 길목을 지나는 단계에서만 `ringsStart`→`ringsEnd`로 퍼졌다 멈추는지.
- 가독성 검사(`tests/e2e/scene-layout.e2e.ts`): 테스트 빌드의 `window.__sceneProbe`가 행위자별 화면 사각형을 준다. 단계가 끝나고 카메라가 멈춘 뒤 등장 행위자가 모두 화면 안에 있고, 부모·자식이 아닌 두 행위자의 겹침(교차 면적 ÷ 작은 쪽 면적)이 20%를 넘지 않아야 한다. 차단 도장은 늘 맨 위에 보여야 하므로 어떤 라벨과도, 이름표·잔액·검사 목록 라벨은 서로 2% 넘게 겹치지 않아야 한다(라벨은 도장·내용 카드 자리를 피하고, 무대 가장자리 안쪽으로 밀려 들어온다). 데스크톱 1440×900, 모든 용어 × 모든 모드.
- `npm run test:e2e`는 `--mode e2e`로 따로 빌드한 `apps/web/dist-e2e`를 대상으로 한다. 용어 × 모드 × 단계마다 JSON 규칙으로 계산한 기대 이벤트 순서와 실제 기록을 비교한다(화면 픽셀 비교는 하지 않는다). 테스트 빌드 전용 `window.__sceneSpeed`로 연출을 빨리 돌린다.
